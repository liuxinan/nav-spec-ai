# 领域知识增强对 DDD 规约生成质量的影响研究

---

## 1. 问题背景

### 1.1 行业痛点

在"自然语言需求 → 可执行代码"的转换链路中，**领域设计规约（DDD）是连接业务语言
与软件实现的关键中间层**。然而，通用大语言模型（LLM）在生成 DDD 规约时存在一个
根本性缺陷：**领域知识盲区**。

通用模型不掌握特定企业内部的术语约定、已有领域模型、业务规则阈值与历史设计资产。
当缺乏领域上下文时，LLM 只能基于通用语义"盲猜"，导致生成的规约与目标工程实际脱节。

### 1.2 具体表现

在 NavSpec AI 流水线中，我们针对同一需求（"导航支持添加途径点功能"）进行了对照实验：

- **对照组**：不注入领域知识，LLM 纯凭通用语义生成 DDD
- **实验组**：注入目标工程的领域知识库（`docs/domain.md`）后生成 DDD

对照组暴露出三类典型问题，每一类都会向下游传导，最终导致编码阶段产出不可用代码。

---

## 2. 方案设计

### 2.1 轻量 RAG：领域知识库注入

PPT 第 10-11 页提出 RAG（检索增强生成）的核心理念——"消除知识盲区，让大模型
看书答题"。完整的 RAG 需要向量库 + 语义检索，对演示场景过重。本工程采用
**轻量 RAG** 方案：

```
目标工程/docs/domain.md    ← 人工编写的领域知识库
        │
        ▼
  scan_project()           ← 扫描阶段自动读取 docs/ 目录下所有 .md/.txt 文件
        │
        ▼
  gen_ddd() / gen_sdd()    ← 作为用户消息的领域上下文，与需求一起喂给 LLM
        │
        ▼
  DDD.md / SDD.md          ← 生成的规约贴合工程实际
```

**实现仅 17 行代码**（`app/stages.py` 的 `scan_project` 末尾），零额外依赖，
修改知识库文件后下次运行即生效。

### 2.2 两层输入的职责划分

LLM 的定位：LLM 不负责最终裁决，必须受到领域知识、Schema 校验
和业务专家的强约束。

本方案将 LLM 的输入严格分为两层：

| 层 | 文件 | 注入位置 | 职责 |
|----|------|----------|------|
| 系统提示 | `standards/ddd_template.md` | System Prompt | **怎么写**：角色、输出结构（6 章）、硬性约束（不编造数值、只覆盖本需求范围、中文+英文代码名） |
| 领域上下文 | `docs/domain.md` | User Message | **写什么**：术语词典、数据结构定义、业务规则、外部服务依赖、模块职责、已知扩展点 |

两层缺一不可：去掉系统提示，LLM 不知道产出什么结构；去掉领域上下文，LLM 产出的
结构正确但内容脱节。

### 2.3 领域知识库的结构

`docs/domain.md` 包含 9 个章节，全部从目标工程实际源码提取：

1. **工程定位**：纯前端单页导航应用，德国境内，开源数据服务
2. **统一语言词典**（19 个术语）：每个术语的代码名、定义、所属模块，如 `LatLng`、`Poi`、`RouteStep`、`NavigationState`
3. **现有数据结构**：完整 interface 定义，含字段类型与单位标注
4. **外部服务依赖**：OpenStreetMap / Nominatim / OSRM 的端点与约束
5. **业务规则清单**（12 条）：每条标注代码依据，如"步骤切换阈值 50 米"来自 `distToStepEnd < 50`
6. **机动动作→中文引导映射表**（17 条）：完整摘自 `buildInstruction` 函数
7. **模块职责与依赖方向**：5 个源文件的分层关系
8. **已知扩展点**（8 个）：含"途径点"扩展提示——"OSRM 支持分号拼接多个坐标"
9. **编码约定**：TypeScript、函数式风格、错误处理模式、坐标顺序约定

## 3. 对照实验结果

### 3.1 术语命名对齐度

这是最直观的差异——直接决定编码 Agent 产出的代码能否与现有工程对接。

| 概念 | 对照组（无知识库） | 实验组（有知识库） | 目标工程实际代码 |
|------|-------------------|-------------------|------------------|
| 地理坐标 | `GeoCoordinate`，字段 `latitude`/`longitude` | `LatLng`，字段 `lat`/`lng` | `LatLng { lat, lng }` |
| 地点 | `Place`（自造抽象） | `Poi`（沿用现有） | `Poi { id, name, address, lat, lng }` |
| 路线字段 | `distanceMeters`/`durationSeconds` | `distance`/`duration` | `Route { distance, duration, steps, geometry }` |
| 导航状态 | 未引用现有类型 | `NavigationState` + 扩展 `currentLegIndex` | `NavigationState { route, currentStepIndex, ... }` |
| 聚合根 | `RoutePlan`（自造，需重命名现有类型） | `Itinerary`（新增）+ 扩展现有 `Route`/`NavigationState` | 对现有结构最小侵入 |

**结论**：对照组要求将 `LatLng` 改名为 `GeoCoordinate`、`Poi` 改名为 `Place`——
这是破坏性重构。实验组直接沿用现有命名，编码阶段零转换成本。

### 3.2 业务规则溯源精度

| 维度 | 对照组 | 实验组 |
|------|--------|--------|
| 规则来源标注 | "导航基本规则"、"地理编码约束"（泛泛） | "OSRM legs 语义 + 现有格式化逻辑"、"工程现有范围限定规则"（精确到代码） |
| 德国边界限定 | 未提及 | BR-04 明确引用 `GERMANY_BBOX` |
| 步骤切换阈值 | "D 米（待确认）" | BR-09 引用现有 50 米阈值 |
| 距离/耗时展示 | 未提及 | BR-02 引用 `formatDistance`/`formatDuration` |
| 兼容性 | 未考虑 | BR-03 "不添加途径点时行为与现状完全一致" |

**结论**：实验组的每条业务规则都有代码级依据，评审阶段可逐条核查；
对照组的规则来源模糊，评审缺乏对照基准。

### 3.3 限界上下文映射

| 维度 | 对照组 | 实验组 |
|------|--------|--------|
| 上下文命名 | "Route Planning Context"、"Place Search Context"（泛化） | 直接映射到 `src/osrm.ts`、`src/guidance.ts`、`src/nominatim.ts` |
| 上下文映射关系 | "发送命令"（简单描述） | Customer-Supplier / Published Language / Shared Kernel（DDD 标准模式，有依据） |

### 3.4 对下游编码阶段的影响

| 影响维度 | 对照组 | 实验组 |
|----------|--------|--------|
| 类型重命名 | 需将 `LatLng`→`GeoCoordinate` 等（破坏性） | 零重命名，沿用现有类型 |
| 改动范围 | 需新增 `RoutePlan` 聚合 + 重构现有模块 | 增量扩展 `Route`（加 `legs`）+ `NavigationState`（加 `currentLegIndex`） |
| 编译通过概率 | 低（类型名不匹配） | 高（类型名一致） |
| 评审可核查性 | 低（规则无代码依据） | 高（每条规则可溯源） |

---

## 4. 结论

领域知识库注入对 DDD 规约生成质量有**显著且可量化**的提升：

1. **术语命名零偏差**——生成的代码标识符与目标工程完全一致，消除编码阶段的类型转换成本
2. **业务规则可溯源**——每条规则标注代码依据，评审阶段可逐条核查
3. **改动范围最小化**——增量扩展而非推倒重来，与现有代码结构兼容
4. **下游传导收益**——术语对齐使 SDD 接口签名准确、编码一次通过率提升、评审有据可查

这一实验验证了：**从"文档驱动"向"规范驱动"的软件生产范式转变中，
结构化的领域知识是消除 LLM 幻觉、保障规约质量的基础设施。**
