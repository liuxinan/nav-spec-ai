# NavSpec AI — 车载导航领域智能需求工程流水线

一句话需求 → DDD 领域设计 → SDD 软件设计 → 自动编码 → 编译仲裁 → 规约评审，全程可人工介入、可回放、零第三方依赖。

## 1. 系统实现目的与背景

### 背景

在车载导航等嵌入式/前端工程中，从"一句话需求"到"可交付代码"之间隔着领域建模、接口设计、编码实现、质量验证多个环节。传统做法依赖资深工程师的经验传递，存在两个典型痛点：

- **规约质量失控**：LLM 直接生成的领域文档术语与工程实际脱节（术语编造、数据结构凭空捏造），下游按错误规约编码，产生级联返工；
- **自动化缺乏仲裁**：端到端 AI 编码"一把梭"，无编译验证、无规约对照，产出不可验收。

### 目的

NavSpec AI 用一条**带人工门禁与双重仲裁的流水线**解决上述问题：

1. **领域知识增强**：自动扫描目标工程 `docs/` 目录的领域知识文档，作为 LLM 生成规约的领域上下文，从源头消除术语偏差（详见 `docs/领域知识增强对DDD规约生成质量的影响研究.md`）；
2. **人工确认门禁**：DDD / SDD 两道门禁，人工可确认、可编辑修订、可驳回（驳回意见结构化回灌重新生成）；
3. **双重仲裁闭环**：先编译（客观，工具链不会撒谎）后评审（主观，以已确认的 SDD 为验收基准），失败自动回灌增量修复；
4. **全程可审计**：每次运行落盘到 `runs/<id>/`，含生成稿/确认稿/事件日志/diff/终态，支持重启后回放与断点恢复。

## 2. 整体架构设计

### 流水线状态机

```
一句话需求
   │
   ▼
┌────────┐   ┌─────────┐   ┌──────────┐   ┌─────────┐   ┌──────────┐
│ 项目扫描 │ → │ DDD 生成 │ → │ 人工确认① │ → │ SDD 生成 │ → │ 人工确认② │
└────────┘   └─────────┘   └──────────┘   └─────────┘   └──────────┘
                ▲    驳回意见回灌 ▲              ▲    驳回意见回灌 ▲
                └────(≤regenLimit)┘              └────(≤regenLimit)┘
   │
   ▼
┌────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
│ 自动编码 │ → │ 编译仲裁  │ → │ 规约评审  │ →   终态     │
└────────┘   └──────────┘   └──────────┘   └──────────┘
   ▲  错误回灌(≤compileRetries) ┘
   ▲  意见回灌(≤reviewRetries) ────┘
终态 outcome：ok / compile_failed / review_failed / rejected / error / interrupted
```

- 编译失败 → 错误结构化回灌，Agent 增量修复；
- 评审判负（以 SDD 契约与 Given/When/Then 验收标准为基准）→ 意见回灌，增量修复；
- 失败运行可 `resume`：跳过 DDD/SDD 与人工确认，直接重入编码→编译→评审闭环，省 token 省时间。

### 模块分层

```
main.py                入口：python main.py 启动 Web 服务（退出码 0 正常 / 3 配置错误）
app/
  config.py            配置加载（config.json + 缺失字段早失败校验）
  web.py               Web 层：纯标准库 http.server，前后端零构建链
  pipeline.py          流水线状态机：运行注册表、人工门禁信令、有界回灌、resume
  stages.py            各阶段实现：扫描 / DDD / SDD / 编码 / 编译 / 评审
  agent.py             LiteAgent：自研轻量编码 Agent（工具模式 + 文本协议降级）
  tools.py             受控工具箱：路径沙箱、命令超时、白名单路由、修改追踪
  llm.py               OpenAI 兼容 LLM 客户端（urllib 直连，支持代理）
  runstore.py          运行持久化：runs/<id>/ 落盘，可回放可审计
web/index.html         前端单页（原生 HTML/JS，轮询快照渲染，无任何前端框架）
standards/             LLM 系统提示模板（结构与约束的单一事实来源）
  ddd_template.md      DDD 生成规范：统一语言表 / 领域模型 / 限界上下文 / 领域事件 / 业务规则 / 待人工确认项
  sdd_template.md      SDD 生成规范：改动总览 / 模块设计 / 接口契约 / 数据流 / 验收标准(BDD)
  coding.md            编码 Agent 行为规范
  review.md            规约对照评审准则（只读，输出 JSON 裁决）
runs/<id>/             每次运行的落盘产物（运行时生成）
docs/                  方案材料：PPT、研究报告、测试用例
```

### Web API

| 方法 | 路由 | 说明 |
|---|---|---|
| GET | `/api/config` | 前端展示用配置（不回传 apiKey） |
| POST | `/api/runs` | 提交一句话需求，创建运行 |
| GET | `/api/runs` | 运行列表 |
| GET | `/api/runs/<id>` | 运行状态快照（前端轮询） |
| POST | `/api/runs/<id>/gate` | 人工确认 / 驳回（驳回必须填意见） |
| POST | `/api/runs/<id>/resume` | 从失败处恢复（跳过文档阶段，直入编码闭环） |

## 3. 关键技术点

1. **领域知识增强（轻量 RAG）**：项目扫描阶段读取目标工程 `docs/` 下的 `.md`/`.txt`（单文件 12K 字符上限防上下文爆炸），连同两层目录结构、README 摘要、package.json 技术栈嗅探，一起注入 DDD/SDD 生成提示词，使规约术语贴合工程实际，不碰源码、不烧 token。

2. **模板即系统提示**：`standards/` 下四个模板分别定义 DDD/SDD 的固定章节结构与硬性约束、编码 Agent 行为准则、评审 JSON 输出格式——结构与约束全部收敛在模板文件中，可审计、可调优，无需改代码。

3. **LLM 只提案不裁决，客观先于主观**：业务阈值等不确定项在 DDD 中显式标注"待人工确认"；闭环先跑真实编译子进程（退出码仲裁），再做只读规约评审；评审输出解析失败时默认判负（fail-safe）。

4. **自研 LiteAgent（纯标准库，双模式自动降级）**：
   - 工具模式：标准 function calling 循环，最多 40 轮必终止；
   - 文本协议模式：服务端不支持工具调用时，要求模型以 ` ```# file: 路径 ` 围栏输出完整文件，正则解析后写盘。

5. **受控工具箱（安全边界）**：编码 Agent 只有 5 个白名单工具（read/write/edit/list/run_command）；所有路径 realpath 解析后必须落在目标仓库内，越界拒绝；命令 180s 超时；追踪本会话写过的文件作为修改感知。

6. **有界重试，费用可控**：编译回灌、评审回灌、文档驳回重生成均有上限（`limits` 可配），到限即终态，不会无限烧钱。

7. **git diff 修改感知 + 按文件配额截断**：编码后 `git diff`（排除 `docs/` 知识库目录）捕获全部改动；评审前按文件分配 24K 字符预算截断 diff，保证每个文件的改动都被评审看到而非被前几个文件占满。

8. **运行持久化与断点恢复**：事件日志 NDJSON 追加、生成稿/确认稿/diff/终态全部落盘 `runs/<id>/`；服务重启后自动恢复历史运行（回放态）；失败运行可 `resume` 复用已确认文档直入闭环。

9. **零第三方依赖**：LLM 客户端（urllib）、Web 服务（http.server）、Agent（自研）全部纯 Python 标准库，`pip install` 无需执行，天然适合演示与内网环境。

## 4. 快速开始

### 前置条件

- Python 3.8+（仅标准库）
- 一个 **git 仓库**形式的目标工程（流水线靠 `git diff` 感知修改），建议其 `docs/` 下放置领域知识文档（如 `domain.md`：术语表、数据结构、业务规则）
- 一个 OpenAI 兼容 LLM 服务

### 步骤

1. 复制配置：

   ```
   cp config.example.json config.json
   ```

2. 填写 `config.json` 关键字段：

   | 字段 | 说明 |
   |---|---|
   | `llm.baseUrl` / `apiKey` / `model` | OpenAI 兼容服务地址与凭证（必填） |
   | `llm.proxy` | HTTP 代理（支持 Basic 认证），留空不走代理 |
   | `target.workdir` | 目标工程路径（必须是 git 仓库，必填） |
   | `target.compileCmd` | 编译/验证命令，如 `npm run build`（必填） |
   | `limits.*` | 有界重试上限（演示场景建议小值） |

3. 启动：

   ```
   python main.py
   ```

4. 浏览器打开 `http://127.0.0.1:8000/`，提交一句话需求（如"支持在导航路线中新增途径点"），在两道人工门禁处确认/编辑/驳回，观察自动编码与双重仲裁闭环。

### 运行产物

每次运行落盘 `runs/<runId>/`：

```
DDD.md / DDD.confirmed.md   领域设计文档（生成稿 / 人工确认稿）
SDD.md / SDD.confirmed.md   软件设计文档（生成稿 / 人工确认稿）
events.ndjson               事件日志（追加写入）
diff.patch                  目标工程的全部代码改动
result.json                 终态结果（程序化消费）
```
